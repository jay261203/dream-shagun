| 18 Nov 2026 | Clients get no insert/update/delete on any table; all writes go through the API with the service role. Guests read published weddings without UPI columns | A guest could otherwise insert a blessing already marked received; API validates and rate-limits (PROJECT.md section 8) |
| 18 Nov 2026 | Dockerize web and api with a `dev` and `prod` target each; docker-compose for local; Supabase stays on the Supabase CLI | Same runtime locally and in production, any service can run alone; Supabase CLI already matches the hosted service |
| 19 Nov 2026 | Family login is Google sign-in first; phone OTP moves to the parking lot | No SMS provider needed to start; the API only checks a Supabase token either way |
| 19 Nov 2026 | Templates are data, not code: the loader rejects raw Handlebars output, script and iframe tags, event handlers and any link to an outside server; all values come from `prepare()` already formatted and URL-checked | Keeps a third-party or future partner template from running code on a guest's phone; see `web/lib/templates/validate.ts` |
| 19 Nov 2026 | The guest page is a route handler (`/w/[slug]`) that returns finished HTML, with its own Content-Security-Policy | Fast first paint and a correct WhatsApp preview; the React slot components (RSVP, blessing) mount later from a script served by us |
| 19 Nov 2026 | Template music is CC0 only: Marigold's default is the veena piece Shri Nilotpala Nayike, played by L Ramakrishnan (Internet Archive item shrInilotpalanayike, also on Wikimedia Commons), trimmed to 90 s MP3. It loads only when a guest taps the button | Music licences are a common trap; CC0 needs no credit but we show one anyway. Wikimedia throttled automated downloads, so the Internet Archive copy was used |
| 19 Nov 2026 | Marigold's default cover photograph is CC BY 3.0 (Biswarup Ganguly); the template footer credits it only when the wedding has no cover photo of its own | CC BY requires attribution wherever the photograph is shown |
| 19 Nov 2026 | "Try with your names" keeps the visitor's draft in the browser (localStorage), not on a server, until they sign in | No account or database row for people who are only looking; nothing to clean up or leak |
| 19 Nov 2026 | The phone-frame preview is an iframe with `sandbox="allow-scripts"` pointing at `/preview/[id]`, which only our own pages may frame and which search engines skip | Template scripts run for the preview but cannot reach our pages or storage |
| 20 Nov 2026 | The browser talks only to the web app. `/api/weddings` and `/api/weddings/slug-check` pass requests on to FastAPI with the login token added on the server | No cross-site (CORS) setup to get wrong, works from a phone on the network, and the token never reaches page scripts. Each POST also checks that it came from our own site |
| 20 Nov 2026 | The API verifies login tokens by the algorithm it is configured to expect: HS256 with the shared secret, or ES256/RS256 with the project's public keys (JWKS). The token cannot choose | Hosted projects, and the local Supabase CLI, now sign with a key pair; a secret-only check rejected every real login. Pinning the algorithm blocks `alg: none` and key-confusion tricks |
| 20 Nov 2026 | The product is light-only (`color-scheme: light`); invitations too | A browser in dark mode otherwise turned the page black behind white cards. A dark theme is a possible later task |
| 20 Nov 2026 | Development runs web, API and database against the local Supabase: `web/.env.development.local` and `api/.env.local` (both ignored by git) sit on top of the hosted values in `.env.local` / `.env`. The API logs why it rejected a token | The web app and the API pointed at different Supabase projects, so valid logins got 401 with no visible reason |
| 17 Nov 2026 | Employment contract check: side project is legal and allowed by the company | Confirmed by Jay; no written approval needed |
| 24 Nov 2026 | Guests are never asked for money on the invitation. A message-only guestbook replaces the blessing form with preset amounts. Gifts become an optional separate page with no preset or minimum amount and no required "did the payment go through?"; the link is on by default only for the wedding occasion. The gift register stays a private host tool, with manual entry, and guest-reported gifts are unverified until the host confirms them | A suggested amount on an invitation can feel like a fundraising page, and a guest saying "I paid" is not proof. Keeping gifts quiet and optional suits weddings and every other occasion |
| 24 Nov 2026 | The gift page is the one place a guest sees a UPI ID, and only when the hosts have not set gifts to off. The setting is stored per invitation (`gift_mode`: off, link, private) and defaults to link until occasion types exist (DS-36), when only weddings will start with it on. The preset-amount blessing routes were deleted rather than kept, so the blessings table has one public write route (the gift note) | A UPI ID has to reach the guest's phone for them to pay, so hiding it was never possible once a pay link exists; the hosts decide whether the page exists at all. Two public write routes for one table is more to defend than one |
| 27 Nov 2026 | A gift a host records by hand counts as received at once and records that host as the one who received it. A physical gift has a description and never an amount, so the rupee totals are only money. Hosts read the register straight from the database (row-level security); every change goes through the API. Any host of the invitation, owner or helper, can use the register | The host typing it in is the one holding the cash or the gift, so asking them to confirm it again adds a step with no proof gained. Mixing an estimated value of a physical gift into money totals would make them wrong |
| 28 Nov 2026 | Home page direction D (a mix of concepts B and C): linen and harbour blue, Chivo, the invitation collage hero, replies beside the live invitation, a word-by-word statement, three steps with real screenshots, a dark close. The product's coral accent and Figtree are replaced app-wide | The owner compared three directions built from the product's real output and chose the mix. Red was wedding-coded and the generic default (design-system.md) |
